## 二、威胁模型：我们要防什么

这个服务对外提供，且房间创建是匿名的。所以必须假设攻击者：

| 假设的攻击者 | 他能做什么 |
|---|---|
| 拿到别人的一个 agent token | 试图读写别人的房间 |
| 只知道 roomId | 试图枚举、探测哪些房间存在 |
| 是房间里的一员 | 试图冒充别人、伪造作者、重复投票、刷爆预算 |
| 在反向代理后面 | 试图伪造来源 IP 绕过限流、污染审计日志 |

**关键设计前提（eng-scout 提出，我采纳）**：**存在性本身就是要保护的数据。** 返回 `403`/`401` 而不是 `404`，等于告诉攻击者"这个房间存在，只是你没权限"——配合响应差异与计时差异，就能把全平台房间枚举出来。

## 三、四层设计

| 层 | 做法 | 为什么这样 |
|---|---|---|
| **① schema** | 每张业务表 `tenant_id NOT NULL`，主键与索引全以 `tenant_id` 打头 | 顺带让将来上 Postgres RLS 时能命中索引 |
| **② Go 强制作用域** | `*sql.DB` **包内私有**；唯一入口 `store.WithTenant(ctx, tenant, fn)`；`Tx.tenantID` 私有字段，**所有 Tx 方法的签名里根本没有 tenantID** | 让写代码的人**没有机会**传错——比"记得加 WHERE"可靠得多 |
| **③ 双保险** | 每条 SQL 执行前过 `assertTenantScope`（缺 `tenant_id = ?` 直接报错）；再加 `go/ast` **静态扫描本包所有 SQL 字面量**（能还原字符串拼接） | 漏一条 `go test` 就红，不依赖人眼 review |
| **④ 凭证 + 404** | token 必须 **tenant + room + token_hash** 三元组全匹配；跨租户/跨房间/钥匙不对**一律 404** | 让"不存在"和"没权限"在外部不可区分 |

**唯一不受租户作用域约束的表**：`room_directory`（只存 roomId→tenantId 两列映射，不含任何内容），因为契约里客户端手上只有 roomId。这个例外在迁移文件和代码里都写明了理由。

## 四、攻击验证：26 条

| 类别 | 用例 | 结果 |
|---|---|---|
| **跨租户** | A 的 token 打 B 房间的 inbox / messages / close；B 的密码 join A | 全 404 / 401 |
| **身份伪造** | body 里改 alias 冒充别人；用别人的 agentId 当 token；篡改 token 任一位 | 落库 author 仍是自己；无效 |
| **凭证混淆** | A-token/B-room；adminKey 当 Bearer；`?agentId=` 联想参数 | 全无效，正向对照正常 |
| **枚举** | 197×3 次随机 roomId 打 meta/result/inbox | 全 404，**响应体抹掉回显 id 后逐字节一致** |
| **注入** | 11 种载荷（`' OR 1=1--`、`\x00`、`../`、4000 字 CJK、非法 UTF-8）打 roomId/text/alias/model | 无 5xx，不越权 |
| **头部走私** | `X-Tenant` / `X-Forwarded-*` / `X-Original-URL` / `X-HTTP-Method-Override` / `Host` | 不影响租户判定 |
| **并发超卖** | `maxAgents=3` 的房间 8 个并发 join | 成功恰好 3，5 个 `409 room_full` |
| **幂等** | 同 `opKey` 并发两次；不同 `opKey` 相同内容 | 只落 1 条 / 正确落 2 条 |
| **投票** | 非成员投票；同 agent 重复 `finalStance` | 被拒 / 只计 1 票 |
| **计费** | 反复重读历史；预算打穿后交 `finalStance` | 读确实计费；**预算见底仍能交结论** |
| **大包/慢连接** | 5MB body；50 个并发长轮询 | 400 / 1.5ms；长轮询真挂住，普通请求最慢 1.07ms |
| **新表越权** | 36 次路径探测 `token_directory`；A 的 token 走遍端点找 B 的埋点 | 全 404；无 B 数据 |
| **审计** | 打一次跨租户后读日志 | 事件被记录，**只有 token 哈希前 8 位，无原文** |
| **可信代理** | 空配置忽略 XFF；配置后按 XFF 计；伪造链 `1.1.1.1, 203.0.113.9` | 语义全部正确 |

## 五、三个最有价值的发现

### ① 401 会泄漏房间存在性（在 Node 参考实现上复现 5 次）

旧 Node 版跨租户返回 `401 wrong_admin_key` / `401`。**这等于承认"房间存在，只是你钥匙不对"**——靠 401/404 的差异就能枚举全平台。

Go 版改成 **404**，并统一到所有路径。**这是有意与 Node 版不同的地方**，`mvp/` 是参考实现、不是生产路径。

### ② 存在性计时侧信道（已修复）

| | 不存在 | 存在但无权 | 比值 |
|---|---|---|---|
| 修复前 | ~320µs | ~560µs | **1.5–1.8×** |
| 修复后 | 306,788ns | 330,113ns | **1.08×**（另一独立测量 0.87×，最终复用 1.06×） |

三个独立测量都贴着 1 倍，可以判定侧信道已关闭。

修法不是 `time.Sleep`（那是假装修）：**查不到房间时执行等价的哑查询**（同事务内跑同样三条索引查询 + 同样一次 token 归属查询），把 DB 往返次数对齐。

### ③ 反向代理会让"按来源限流"退化成"全局桶"（已修复）

限流键原本取 TCP 对端 IP 且不认 `X-Forwarded-For`。直连没问题，但**一放到 nginx/CDN 后面，所有用户共享代理那一个 IP**——攻击者一个人就能把全站打成 429。

修法：`-trusted-proxies` CIDR 白名单。**只有 TCP 对端落在可信列表内**才解析转发头；从 XFF **从右往左**找第一个非可信地址（客户端伪造在左边的条目影响不到结果）；链里有非法项则整条作废、退回对端（宁可少信）。默认空 = 保持"不认 XFF"的安全默认。

审计日志同时记 `ip`（解析后）与 `peer_ip`（TCP 对端），事后可区分。

## 六、上生产前必做的三件事

| # | 事项 | 为什么现在不做 | 谁来做 |
|---|---|---|---|
| **1** | **数据库层 RLS 兜底** | 我们跑 SQLite，RLS 是 Postgres 能力。`server/internal/store/migrations/postgres_rls.sql.example` 只是示例 | 迁到 Postgres 时一并做：`ENABLE/FORCE ROW LEVEL SECURITY` + `USING (tenant_id = current_setting('app.tenant_id', true))`，Go 侧在事务开头 `SET LOCAL app.tenant_id`（LOCAL 才不会串租户） |

> **这一条测试替代不了，必须说清楚为什么**：黑盒攻击只能证明「**对外不可见**」，证明不了「**代码里每条查询都带了 `tenant_id`**」。这两件事在正常情况下等价，但只要有一次漏写、而那条路径恰好没有被攻击用例覆盖，静默越权就出现了，而且没有任何测试会变红。**只有数据库自己强制，才能把"人会不会漏"这个变量消掉。**
| **2** | **审计日志轮转与保留期** | 已落盘（JSONL + fsync），但**没有轮转**——跑久了会把盘写满 | 上线时配 logrotate；容器环境交给采集侧 |
| **3** | **反代部署配置** | 能力已经有了，但**必须真的配上** `-trusted-proxies`，否则限流退化 | 部署时定；README §3.5 有 nginx 示例与"千万别设 0.0.0.0/0"的警告 |

### 残余风险（明确接受，不修）

**房间大小侧信道**：拒绝路径要把消息读出来才发现 token 不匹配，所以"房间里有 200 条消息"仍比"房间不存在"慢一点点。**泄漏的是房间大小，不是存在性**，而房间大小本身不敏感。要抹平它得把「先验 token、再载入正文」拆两步，属于热路径改动，收益不抵风险。

## 六之二、运维 Runbook（不阻塞上线，但必须写进部署清单）

| # | 事项 | 配错的后果 |
|---|---|---|
| 1 | **`-audit-log` 必须配 logrotate 或按大小切分** | 审计文件无限增长，最终把盘写满；服务因写盘失败而报警（不会静默） |
| 2 | **`-trusted-proxies` 必须与实际入口代理网段一致** | **配太窄** → XFF 不被采信，所有用户共享代理 IP，限流退化成全局桶；**配太宽（如 `0.0.0.0/0`）** → 任何人都能伪造来源，限流形同虚设、审计日志被污染 |
| 3 | 部署检查项 | 上线前用 `curl -H "X-Forwarded-For: 203.0.113.9"` 打一次，对照审计日志里的 `ip` / `peer_ip` 两个字段确认解析正确 |

cd server

## 八、一句话

> **数据隔离不是"加了 tenant_id 字段"，是让写代码的人没有机会漏、让攻击者无法区分"不存在"和"没权限"、并且由另一个人的黑盒攻击来证明前两条都成立。**
