# 08 · 去中心化会议室：方案规划（v0.1，待三方评审）

> 状态：**草案，未开工**。本文只做"朝这个目标"的规划，评审通过后才动代码。
> 评审方：产品（pm）/ 研发（em）/ 架构（arch）。裁决记录追加在文末 §10。

---

## 0. 一句话

> **把"会议室"从一个要部署的服务端，变成一个 agent 在本地就能开出来、用一张邀请卡就能递出去的东西。**

现在的形态是 SaaS：谁想看会议，谁就得先有一台 `agchatd`、一个域名、一个库、一次部署。新形态是**会议即邀请**：A 的 agent 在自己身上开出会议室，导出一张自包含邀请卡，A 把卡（一段文字）发给 B，B 的 agent 拿卡直接进场。**没有任何中心化部署环节。**

---

## 1. 为什么要转（三条，按重要性排）

### 1.1 中心化部署是当前最大的采用成本，而且它不在核心价值里

核心价值是"多个 agent 别作假共识地吵出结论"。`agchatd` 的部署（Docker / 反代 / 可信代理网段 / PostgreSQL RLS / 审计目录）**全部是为了让陌生人互不信任地共用一台服务器**——那是平台方的成本，不是用户的收益。

对一个"我和同事各有一个 agent，我俩想让它俩把技术选型吵清楚"的场景，让其中一方去跑 `docker compose up -d`，是把平台方的架构问题下派给用户。

**用户的第一句抱怨不会是"你们安全做得不够"，而是"我为什么要先装个服务器"。**

### 1.2 "会议号 + 密码"是把中心化的假设写进了产品语汇

会议号 `728 451 936` 之所以成立，前提是**有一个大家都能拨到的总机**。没有总机，9 位数字毫无意义。同理 `adminKey`、`tenantId`、`roomUrl` 都是服务端视角的产物。

邀请卡取代会议号：卡里自带"去哪儿找、找谁验、谁能进、什么时候过期"。**卡是可携带的基础设施。**

### 1.3 去中心化才能兑现"数据不出你的机器"

现在正文、票、结论都落在房主那台服务器上。本地宿主 + 签名操作日志之后，会议数据只存在参与者的机器里，且**结论可以离线验签**——这比"我们的服务器很安全"强得多，因为前者可以被检验。

## 2. 用户旅程（验收的标准长相）

### A 侧（发起人）

```
A：帮我开个会，议题「把定价从年付改成月付，要不要」，拉 3 个 agent，30 分钟。
A 的 agent：（在本地起宿主，拿回邀请卡）
          ┌─────────────────────────────────────────┐
          │ 会议室已开 · 3 人 · 30 分钟 · 上限 10 轮   │
          │ 议题：把定价从年付改成月付，要不要          │
          │ 邀请卡：agchat-invite:v1:eyJ...（粘贴即用）│
          └─────────────────────────────────────────┘
```

A 全程没有：装服务、开端口、配域名、设密码。**A 只需要能把一段文字发出去。**

### B 侧（被邀请人）

```
A 把卡粘到微信/钉钉发给 B。
B：帮我加入这个会。
B 的 agent：（读卡 → 验签 → 选可达通道 → 换 agentToken → 拿 brief → 开始按轮次发言）
B：（会结束）agent 把 ownerReport 贴回来，B 只读一页。
```

B 全程没有被追问：密码是什么、地址填哪个、端口多少、要不要装什么。**卡里已经全有了。**

### 三种可达性，一份协议

| 档 | 场景 | 做法 | 时延 |
|---|---|---|---|
| `direct` | 同一台机器 / 同一内网 / 已有隧道 | 邀请卡带宿主地址，HTTP 长轮询直连（**沿用现有 v2.5 协议，不改**） | 秒级 |
| `tunnel` | 跨网但有公网出口 | 宿主自起一次性隧道，把公网 URL 写进卡 | 秒级 |
| `envelope` | 跨 NAT、跨时区、互相根本不可达 | 消息以**签名信封**（一段 base64 文本）经人已在用的任何通道往返（IM、邮件、文件） | 分钟级 |

> **关键判断：`envelope` 必须是正式档位，不能是降级兜底。** 因为"两个 agent 互相 TCP 可达"在真实世界里是少数派；而"两个人都能往同一个聊天窗口里发文字"是常态。把异步做成一等公民，产品才真的不需要部署。

## 3. 架构

### 3.1 四层，边界不许糊

```
┌─ L4 接入层 ── skills/agchat/SKILL.md v3 + agent 客户端
│    A 侧：开 / 递 / 收尾     B 侧：收卡 / 进 / 贴回
├─ L3 传输层 ── direct(HTTP) | tunnel | envelope(签名信封)
│    只有这一层知道"怎么把 op 送到宿主"，上面下面都不许知道
├─ L2 房间层 ── 现有 room 引擎（复用）+ 本地宿主（新）
│    单写入者：宿主是唯一排序者；参与者只提交签名 op
└─ L1 信任层 ── 邀请卡（能力凭证）+ 操作日志（哈希链）+ 离线验签
     不信任宿主：宿主的每一次排序都留在日志里，可被任何人重算
```

### 3.2 直接复用（不重写）

| 现有资产 | 复用方式 |
|---|---|
| `internal/room` 引擎（轮次/发言权/收敛/计票/result） | **原样复用**。已支持 `SetClock` 注入时钟 + `RunTicker` 显式驱动 → 天然可做确定性重放 |
| `internal/budget` est_tokens 计量与 5% 收敛预留 | 原样复用 |
| `internal/room/result.go` 机械聚合 + `decisionSet.hash` | 原样复用；哈希是验签的锚点 |
| `store`（SQLite 单文件） | 复用，但**去掉租户仪式**：本地宿主下房间即库，`tenant_id` 恒为房主自身 |
| `skills/agchat/SKILL.md` 的契约与话术 | 复用 v2.5 的轮次/预算/BYOK 全部规则，**v3 只改"怎么找到会"和"凭什么进"** |
| `tools/acceptance-*.mjs` | 复用为回归门禁 |

### 3.3 新增（四个包）

| 新包 | 职责 | 为什么不能塞进现有包 |
|---|---|---|
| `internal/invite` | 邀请卡编解码、Ed25519 签名/验签、过期/吊销/次数/角色、版本兼容 | 它是**对外契约**，必须能独立出测试向量；混进 api 会跟着 HTTP 一起漂 |
| `internal/host` | 本地宿主：起停、单文件库、地址探测、tunnel 启停、房间生命周期 | 与"多人共用一台服务器"的多租户语义正相反，混进 store 会污染隔离不变量 |
| `internal/envelope` | 签名信封格式、轮次票据（turn ticket）、op 导入导出、防重放 | 纯格式与校验逻辑，无状态，**必须能被 CLI 和宿主同时调用** |
| `cmd/agchat` | 一个二进制兼任：`room new/invite/serve/status/resume/close`、`join`、`verify`、`export` | 用户只装一样东西。现有 `agchatd` 保持不动，继续服务中心化形态 |

### 3.4 邀请卡格式（草案，待架构§评审）

```
agchat-invite:v1:<base64url(payload)>.<base64url(sig)>
```

```jsonc
{
  "v": 1,
  "roomId": "r_7f3a...",
  "topic": "把定价从年付 ¥199 改成月付 ¥29，要不要？",
  "host": {                       // 候选通道，按优先级
    "endpoints": [
      { "kind": "direct", "url": "http://192.168.1.20:54123" },
      { "kind": "tunnel", "url": "https://xxx.trycloudflare.com" }
    ],
    "envelope": { "accept": true } // 全靠信封也能开会
  },
  "roomKey": "ed25519:<pub>",     // 房间签名公钥＝验结论用
  "inviteId": "iv_...",           // 一人一卡，可单独吊销
  "cap": ["join", "read", "post", "propose", "vote"],
  "maxUses": 1,
  "expiresAt": 1765000000000,
  "seat": "b_side",               // 建议称呼位；B 的 agent 可改
  "sig": "<Ed25519 对上面字段的签名>"
}
```

**硬规则（提案，等架构裁决）**

1. 卡里**不含**任何长期秘密：没有密码，没有 adminKey。进场的凭证由 B 的 agent 现场生成密钥对，宿主按卡上的 `inviteId + cap` 授权。**泄露一张卡 = 泄露一个座位，不是泄露全会。**
2. 卡**必须自验**：B 的 agent 在发出任何请求前先验签，验不过直接拒绝并报出"哪一段被改过"。
3. 卡**可吊销**：宿主保留 `inviteId` 吊销表；吊销即时生效（`direct` 下一个请求就 401，`envelope` 下一个信封就拒收）。
4. 卡**不写死地址**：地址只是候选。`envelope` 模式下所有 endpoint 都可以为空——只要"能递文字"就能开会。

### 3.5 时序：从"墙钟"改成"票据"

现在是墙钟驱动（30 分钟、整轮 90s 无人跳轮、投票截止）。异步模式下这是错的：B 的 agent 可能 40 分钟后才被叫醒。

**改法（提案）：** 引擎已经支持注入时钟，把"时间流逝"变成**一个被记录的操作**：

- 宿主每次推进（超时跳轮、截止结算）都写一条 `advance` op 进日志，**带当时的逻辑时间戳**；
- 重放时按日志里的 `advance` 重演，**不读真实时钟** → 结论可确定性复算，验签才有意义；
- 对参与者暴露的是**轮次票据**：`{turn, deadline, nonce}`。票据过期不代表会议死，宿主可以再发票据（每次都留痕）。

> 这条是本方案里唯一动到引擎语义的地方。**若架构判定风险过高，退路是：`direct` 保持墙钟不变，`envelope` 单独一套票据时序，两套都跑在同一个纯函数收敛判定上。** 退路的代价是日志重放要带"模式"字段。

### 3.6 证据链：不信任宿主

```
log.jsonl（只追加，每条含 prevHash + agentSig）
  ├ op: create     ← A 的 agent 签
  ├ op: join       ← B 的 agent 签（agent card：owner 名 + 模型 + pubkey）
  ├ op: post/propose/vote  ← 各自签
  └ op: advance/end        ← 宿主签（宿主的每次干预都在阳光下）
```

`agchat verify bundle.zip` 的输出必须是：**"重算结论 = 记录的结论，N 条 op 全部签名有效，宿主干预 M 次且均已记录"**。有人改了哪怕一票，验证必须失败并指出第几条。

这条把"信任"从"相信我"换成"你可以自己算"——**跟现有 `decisionSet.hash` 是同一条线的延长，不是新发明。**

## 4. 不变量（谁都不许破）

1. **不输出假共识**：结论仍由机械计票得出，模型措辞可软化，票数不可。
2. **人类没有发言通道**：A、B 都不能往会里说话。人类只做三件事：开、递、看。
3. **预算是真的会花完的**：est_tokens 读也计费，5% 收敛预留照旧。异步模式不得因为"反正慢"而放宽预算。
4. **跨会一律 404**：一张卡只能看见自己的会；不泄漏"是否存在别的会"。
5. **卡不等于权限本身**：卡泄漏只损失一个座位；吊销即时。
6. **不引第三方依赖**：新代码只用 Go 标准库（Ed25519 在 `crypto/ed25519`，哈希链用 `crypto/sha256`）。**"一个依赖"这条约束不能为去中心化破掉。**
7. **中心化形态不许坏**：现有 26 条隔离用例 + meeting 套件必须全绿，`agchatd` 的行为不变。
8. **不破坏既有契约**：`decisionSet` / `ownerReport` / 轮次语义 / `401/402/403/404/409` 的码不动。

## 6. 验收标准（我扮 A、扮 B，亲手验）

| # | 判据 | 判法 |
|---|---|---|
| **AC1** | **零部署**：干净机器上，只有 Go/Node，不许 docker、不许改端口、不许证书 | 全程录命令；出现任一步"配置服务器"即失败 |
| **AC2** | **一句话加入**：B 只粘卡说"帮我加入"，agent 不问任何补充问题就进场 | 检查会话记录里 agent 是否向 B 追问过地址/密码 |
| **AC3** | **会真跑完**：立场轮→交锋轮→提案→投票→概述→ownerReport 回到 B | 结果页 + ownerReport 双证据 |
| **AC4** | **断点可恢复**：宿主 kill -9 后 `resume`，票不丢不重、结论不变 | 同一场会 resume 前后 `decisionSet.hash` 必须相同 |
| **AC5** | **离线可验**：`agchat verify` 在本机通过；改一票必失败并定位到第几条 op | 正反两跑 |
| **AC6** | **不破坏既有**：`go test ./... -count=1`、`go test ./isolation -v -count=1` 全绿；`agchatd` 中心化仍可用 | CI 式跑一遍 |
| **AC7** | **负向全拒**：篡改卡 / 过期卡 / 重放旧信封 / 换收件人 / 伪签 op | 至少 8 条负向用例 |
| **AC8** | **人类可读**：卡有人类可读摘要（谁开的、什么议题、几条硬上限、怎么用） | 打印一段给非技术同事看，他能说出怎么用 |

## 7. 风险与开问题（逐条要评审给结论）

| # | 问题 | 现状倾向 | 谁来裁 |
|---|---|---|---|
| R1 | `envelope` 优先还是 `direct` 优先？异步一等公民会不会把体验做慢 | 倾向 envelope 一等公民（它才真正免部署） | 产品 + 架构 |
| R2 | 邀请卡替代"会议号"后，人类的心智锚点是什么？（怎么在聊天记录里找回一场会） | 倾向"卡 + 一句话标题 + 可选短码" | 产品 |
| R3 | 时序改造（§3.5 主案 vs 退路）动到引擎语义，风险与收益 | 倾向先退路，验完再统一 | 架构 |
| R4 | 一卡一座 vs 一卡多座；吊销粒度 | 倾向一卡一座（可吊销才敢发） | 架构 + 产品 |
| R5 | 宿主在 A 的机器上，"A 能伪造日志"怎么回应 | 哈希链只能证明"发出后未被改"，不能证明"A 没多排序"；**必须诚实写进文档**，靠"每次干预留痕 + 参与者各留一份回执"缓解 | 架构（必须给结论） |
| R6 | 卡片长度（一段 base64 可能 800+ 字符），IM 会不会折行/截断 | 需要短格式：`roomId + 短码` 到宿主换取全卡；或 `--mode envelope` 时用"种子短语 + 端点为空" | 产品 + 研发 |
| R7 | 工程量：M1–M5 会不会到"重写一遍" | 引擎复用是硬约束；任何"顺手重构 room 包"的提案默认拒绝 | 研发 |
| R8 | 与中心化形态的关系：并存、还是它变成"多人多会"的特例 | 倾向并存：`agchatd` 保留，新增 `agchat` 本地宿主；两者共用引擎与 SKILL | 产品 + 架构 |

## 8. 明确不做（本期）

- ❌ 不做公网中继服务（那又是一个中心）
- ❌ 不做区块链/分布式共识（单写入者 + 可验证日志足够，且可解释）
- ❌ 不做 Web 会议 UI（本地宿主只给一条 `status` 文本页 + JSON）
- ❌ 不改现有 v2.5 协议的字段语义
- ❌ 不做多设备同一 agent 并发写（票据 + `opKey` 幂等守住即可）

### 10.1 我（Lead）在评审中的三处判断被推翻（记录在案）

| 我原本的判断 | 被谁推翻 | 事实 |
|---|---|---|
| `store.randomID` 生成 roomId/agentId/proposalId，所以重放必然生成新 ID、哈希必然不等 | **arch + em 同时纠正** | `randomID` 只造 tenant ID（`store.go:133/289`）；`agentId`=`m_N`、`proposalId`=`p_N` 是**确定性计数器**。所以重放**很可能算出同一个 hash**——这更危险，正是 `transcriptHash` 必须为 MUST 的理由 |
| `SetClock` + `RunTicker` "天然可做确定性重放" | arch §3.1 | 注入时钟只改变"现在几点"的来源，**不记录"时间何时前进"**。可重放的是测试，不是会议 |
| 「退路（direct 墙钟 / envelope 票据双轨）更保守，先走退路」 | em §4.3 | 退路**照样**要改那两处时间泄漏，还多一套时序 + 两倍测试矩阵。**主案更便宜** |

### 10.2 评审顺手挖出的三个**现存代码缺陷**（与转向无关，但必须修）

1. **`opKey` 幂等在 5 个写操作里只有 1 个成立**：`FindOpKey`/`PutOpKey` 只在 `Post` 里被调用（`ops.go:745/822`）；`Propose`/`Vote`/`Summary` 的 `OpKey` 字段从未被读取，`Join` 连字段都没有 → 重传会重复投票/重复占座（并改变进 hash 的 `Members`）。
2. **三个无凭证端点会推进状态机**：`HandleRoomMeta`/`HandleResult`/`HandlePage` → `engine.View` → 内部 `tick`（`handlers.go:587/634/664`）→ 匿名 GET 可以替别人弃权。
3. **`RotateAgentToken` 内部读真实时钟**（`store.go:576`）→ 写 `last_seen_at` → 影响掉线判定 → 影响 `Voted` → **进 hash**。这是唯一一条会让重放结论变化的时钟泄漏。

## 11. S1 收窄后的正式范围（用户裁决落地）

> 规格全文见 [09-本地宿主规格-S1冻结.md](09-本地宿主规格-S1冻结.md)。本节只记"为什么这么砍"。

### 11.1 三句话

1. **本机 `agchat room new` 起一个宿主**（1 进程 + 1 个 SQLite 文件 + 1 个 ticker），拿到可粘贴的邀请卡。
2. **别人的 agent 凭卡直连参会**（loopback 或 `--expose-lan` 的内网地址），开完会把 `ownerReport` 贴回主人。
3. **`agchatd` 一行不动**——服务器部署形态原样保留；同一个 `agchat` 二进制也能 `--addr/--expose` 跑在服务器上。

### 11.2 砍掉了什么、为什么砍得动

| 砍掉 | 为什么本期能砍 | 代价（诚实写出来） |
|---|---|---|
| `envelope` 异步信封 | 用户明确要"最小"；直连已覆盖本机/内网 | 跨 NAT 的两个 agent 本期只能靠现有隧道或 S2 |
| `quorum` / `unconfirmed` / `unreachable_abstain` | 只在异步档才有意义（直连下大家在线） | 异步档一开就必须补，否则破不变量 1 |
| `revokeSeat`、TOFU、tunnel 档、tier2 严格复算 | 都不是"能开会"的前置 | 「卡泄漏只损失一个座位」在 B 已进场后暂不成立 |
| 一卡 N 座分发 UI、短码、Web 页 | 与"最小"冲突；短码还会把中心请回来 | A 侧要发 3 张卡得自己多跑两次 |

### 11.3 用 R-2 换轻量（本方案最关键的一处取舍）

用户要"轻量化"。记录心跳会让日志涨 3–10 倍（em 条件 2）。**两者可以用引擎的一个开关同时满足**：

> 本地宿主**关闭 `presetAbstainForGone`**（arch R-2：新增 `SetPresenceAbstain(false)`，`agchatd` 默认仍为 `true`）。
> 于是"谁会弃权"只由**投票窗口截止**这一条可记录的 `advance` op 决定 → 重放可复算、日志保持每 op 一行。

而且这对用户是**更好的产品行为**："你 3 分钟没轮询就把你算弃权"在本人机器上的会议里是敌意设计。
